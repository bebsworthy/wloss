Friday 17:24 — the week, mid-flight.
  1. 1Fit badges show the gap, never a verdict: “kcal ✓ · P −6 g”; ✓ means within ±5 % kcal (R-S7), aligned with F07’s proposal semantics so a fit plan never argues with a held week. Saturday’s hand-placed lamb renders “kcal +12%” — the number is the information; no fail state exists. Badges flip in like split-flap after the 40 ms deal-in.
  2. 2Week targets carry provenance (“updates weekly · Sep 6”) — plans generate against today’s budget, not onboarding’s; Sunday’s Apply (→ flow 03) re-solves only the slots the new targets violate.
  3. 3Skipped slot, zero guilt — the spec’s own copy, verbatim: “Friday’s plan met real life — replanned.” Skips feed adherence honestly; the state machine (planned → confirmed / swapped / skipped / replaced) is owned by F03 (R-B1 treaty: F02 owns nutrition of replacements).
  4. 4Leftover connector: stitched tupperware line from Tue’s cook event to Wed’s lunch; ingredient weight is charged to the cook day only, so the list pays for cook events, not eating events; tap pans the calendar to the parent batch.
  5. 5Adherence strip: zipper-extends per confirm; below 3 logged days it renders “not yet meaningful” — the metric answers “how good is my planning?”, never “how good are you?” (“plans that survive contact with Tuesdays”, F03 §6).
  6. 6Build list opens F04 with the week pre-selected; the list exists < 1 s after the plan does — the chore that kills meal planning, designed out.
  7. 7“Why this plan” — visible reasoning: overlap edges, hardest rules, waste-avoided (≈ €4.10, forward-framed). Library too small? Unfillable slots get the neutral “add anything” card with the reason (“nothing vegetarian … — add/import, or relax one rule with a tap”), never a blank failure. Deterministic engine, on-device — no consent needed in v1 (R-S10); cloud generation is [v1.x] behind the `meal-planning` toggle.
